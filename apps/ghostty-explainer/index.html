Ghostty: The Contributor's Guide

An interactive explainer for developers who want to understand and contribute to Ghostty, a fast, native, feature-rich terminal emulator written in Zig.

What is Ghostty?

Ghostty is a terminal emulator that differentiates itself by being fast, feature-rich, and native. Unlike many terminal emulators that force you to choose between these qualities, Ghostty provides all three.

  • Fast: Multi-renderer architecture (Metal on macOS, OpenGL on Linux), dedicated IO thread, SIMD-optimized parsing
  • Feature-rich: Full standards compliance, ligatures, Kitty graphics protocol, shell integration
  • Native: True SwiftUI app on macOS, GTK on Linux - not a lowest-common-denominator cross-platform UI
~100k Lines of Zig
3 Renderers (Metal, OpenGL, WebGL)
2 Platform UIs (SwiftUI, GTK)
Zig 0.15+ Language Version

Threading Model

Ghostty uses a multi-threaded architecture for optimal performance:

Main Thread

  • UI event loop (GTK/AppKit)
  • Window management
  • Input handling
  • Configuration

I/O Thread

  • PTY read/write
  • Terminal parsing
  • Screen state updates
  • Low-jitter under heavy load

Render Thread

  • GPU rendering
  • Frame pacing
  • Font atlas management
  • Custom shaders

Why separate threads? Heavy I/O (like cat large_file.txt) shouldn't block rendering, and rendering shouldn't block input processing. The I/O thread can process incoming data while the render thread is busy drawing the previous frame.

Key Components

Understanding these core components is essential for contributing to Ghostty.

Surface

src/Surface.zig

The central "widget" that represents a single terminal. It owns:

  • Terminal I/O handler (termio.Termio)
  • Renderer instance
  • Font configuration
  • Input state (keyboard, mouse)
  • Configuration

At ~6,000 lines, this is the largest file. It coordinates all the pieces that make up a working terminal.

Terminal

src/terminal/Terminal.zig

The primary terminal emulation structure. Manages:

  • Grid of characters (cells)
  • Scrollback buffer
  • Cursor position and style
  • Terminal modes (DEC private modes)
  • Mouse tracking state
  • Color palette
pub const Terminal = struct {
    screens: ScreenSet,           // Primary & alternate screens
    tabstops: Tabstops,
    rows: size.CellCountInt,
    cols: size.CellCountInt,
    scrolling_region: ScrollingRegion,
    colors: Colors,
    modes: modespkg.ModeState,
    // ...
};

Parser

src/terminal/Parser.zig

VT-series parser based on the vt100.net state machine. Handles:

  • ANSI escape sequences
  • CSI (Control Sequence Introducer) commands
  • OSC (Operating System Command) sequences
  • DCS (Device Control String) sequences
pub const Action = union(enum) {
    print: u21,              // Draw character (unicode codepoint)
    execute: u8,             // Execute C0/C1 function
    csi_dispatch: CSI,       // CSI command
    esc_dispatch: ESC,       // ESC command
    osc_dispatch: osc.Command,
    dcs_hook: DCS,
    // ...
};

Screen & PageList

src/terminal/Screen.zig, src/terminal/PageList.zig

The screen manages the visible grid and scrollback:

  • Screen: Current viewport into the scrollback
  • PageList: Efficiently manages pages of terminal history
  • Page: A chunk of terminal rows with cells
  • Supports millions of lines of scrollback

Renderer

src/renderer/

Ghostty has a multi-renderer architecture:

Metal macOS/iOS (native, best performance)
OpenGL Linux (OpenGL 4.3+)
WebGL Browser/WASM (experimental)

The GenericRenderer provides shared rendering logic, while backends handle GPU-specific operations.

Font System

src/font/

Comprehensive font handling:

  • Discovery: CoreText (macOS), Fontconfig (Linux)
  • Rendering: FreeType for glyph rasterization
  • Shaping: HarfBuzz for complex text layout & ligatures
  • Atlas: Texture atlas for efficient GPU rendering
  • Fallback: Automatic font fallback for missing glyphs

Terminal I/O (termio)

src/termio/

Handles communication with the PTY:

  • Backend: PTY allocation and process management
  • Mailbox: Thread-safe message passing
  • StreamHandler: Processes terminal data stream
  • Supports shell integration hooks

Configuration

src/config/Config.zig

At ~10,000 lines, the config system is extensive:

  • 200+ configuration options
  • File-based configuration (~/.config/ghostty/config)
  • Runtime reloading
  • Conditional configuration (light/dark mode)
  • Keybinding system

Design & Tradeoffs

Understanding the design decisions and tradeoffs helps you make contributions that align with the project's philosophy.

Core Design Principles

1. Native UI, Shared Core

Ghostty rejects the "write once, run anywhere" approach for UI. Instead:

  • macOS: Real SwiftUI/AppKit app developed in Xcode, with native menus, preferences, and behaviors
  • Linux: GTK4 with libadwaita for a native GNOME experience
  • Core: Terminal emulation, rendering, and I/O are shared Zig code
Tradeoff: More code to maintain (Swift + GTK + Zig), but users get a truly native experience. The macOS app is a genuine first-class macOS citizen, not a web app in disguise.

2. libghostty Architecture

The macOS app doesn't compile the Zig code directly. Instead:

  1. Zig code compiles to libghostty (a C-compatible static library)
  2. Swift app links against libghostty via C headers
  3. Swift's main() is the entry point, calling into libghostty
// C API example (simplified)
ghostty_init(argc, argv);
ghostty_surface_t* surface = ghostty_surface_new(config);
ghostty_surface_draw(surface);
Tradeoff: More complex build system, but enables true native UI development and opens the door for embedding Ghostty in other apps.

3. Multi-Threaded by Design

Ghostty uses dedicated threads for I/O and rendering:

  • I/O Thread: Reads from PTY, parses escape sequences, updates terminal state
  • Render Thread: Draws frames to screen, manages GPU resources
  • Main Thread: Handles UI events, input, configuration
Tradeoff: Complexity of thread synchronization, but essential for performance. Heavy I/O won't block rendering, and rendering won't block input.

4. Standards First, Then xterm, Then Others

Terminal behavior priority:

  1. ECMA-48/ANSI standards when they exist
  2. xterm behavior for unspecified features
  3. Other popular terminals (Kitty, VTE) as fallback

Ghostty maintains a comprehensive xterm audit to ensure compatibility.

5. Performance Without Sacrifice

Key performance decisions:

  • SIMD parsing: Uses Highway library for vectorized terminal parsing
  • Metal renderer: Direct Metal (not MoltenVK) for macOS, with ligature support
  • Efficient scrollback: PageList uses chunked allocation for millions of lines
  • Lazy font loading: Fonts are loaded on-demand from a SharedGridSet
Tradeoff: More complex implementation, but Ghostty can cat large files 2-4x faster than many competitors while still supporting ligatures and rich features.

Notable Design Decisions

Why Zig?

Zig was chosen for several reasons:

  • Excellent C interop for using FreeType, HarfBuzz, GTK, etc.
  • No hidden allocations or control flow
  • Comptime (compile-time execution) for configuration and code generation
  • Cross-compilation support built-in
  • Memory safety features (bounds checking, use-after-free detection in debug)

Why Not Electron / Cross-Platform UI?

Ghostty prioritizes native experience over development convenience:

  • Native apps are faster (no JavaScript runtime)
  • Native apps use less memory
  • Native apps feel right on each platform (gestures, menus, accessibility)
  • Terminal power users are exactly the audience that notices these differences

Configuration Philosophy

Ghostty uses a simple key-value config format (not TOML, YAML, or JSON):

# ~/.config/ghostty/config
font-family = JetBrains Mono
font-size = 14
theme = Dracula
window-decoration = false

The format is intentionally simple and doesn't require parsing libraries. Config is hot-reloadable.

Zig Primer for Contributors

A quick introduction to Zig concepts you'll encounter in the Ghostty codebase.

Note: Ghostty requires Zig 0.15.2+. The language is pre-1.0 and evolves rapidly. Check ziglang.org for the latest documentation.

Key Concepts

Allocators

Zig has no hidden memory allocation. Every allocation is explicit and requires an allocator:

// Allocator is passed explicitly - no hidden malloc()
pub fn create(alloc: std.mem.Allocator) !*App {
    var app = try alloc.create(App);
    errdefer alloc.destroy(app);
    try app.init(alloc);
    return app;
}

// Common allocators in Ghostty:
// - std.heap.c_allocator (wraps malloc/free)
// - std.heap.GeneralPurposeAllocator (debug allocator)
// - ArenaAllocator (bulk free, no individual dealloc)

Error Handling

Errors are values, not exceptions. The ! operator propagates errors:

// Function that can fail returns !T (error union)
pub fn init(self: *App, alloc: Allocator) !void {
    var font_grid_set = try font.SharedGridSet.init(alloc);
    errdefer font_grid_set.deinit();  // Cleanup on error
    // ...
}

// Caller can propagate with try or handle explicitly
state.init() catch |err| {
    std.log.err("failed to init: {}", .{err});
    return 1;
};

Comptime (Compile-Time Execution)

Zig can execute code at compile time. Ghostty uses this extensively:

// Compile-time conditional compilation
pub const Renderer = switch (build_config.renderer) {
    .metal => GenericRenderer(Metal),
    .opengl => GenericRenderer(OpenGL),
    .webgl => WebGL,
};

// Comptime parsing for terminal escape sequences
const table = @import("parse_table.zig").table;
// ^ This table is built at compile time, not runtime

Optionals and Null Safety

Null pointers are explicitly typed as optionals (?T):

// Optional type - can be null
focused_surface: ?*Surface = null,

// Must handle null case explicitly
pub fn focusedSurface(self: *const App) ?*Surface {
    const surface = self.focused_surface orelse return null;
    if (!self.hasSurface(surface)) return null;
    return surface;
}

// orelse provides default, .? unwraps (panics if null)
const value = optional orelse default_value;
const ptr = optional.?;  // Panic if null

Slices and Arrays

Zig distinguishes between arrays (fixed size) and slices (pointer + length):

// Array - fixed size, stored inline
var buffer: [1024]u8 = undefined;

// Slice - pointer + length, can point to any contiguous memory
fn process(data: []const u8) void {
    for (data) |byte| {
        // ...
    }
}

// Sentinel-terminated slice (like C strings)
const c_string: [*:0]const u8 = "hello";
const zig_slice: [:0]const u8 = "hello";

Structs and Methods

Zig structs can have methods, but there's no implicit this:

const Surface = @This();  // Gets current struct type

pub const Surface = struct {
    alloc: Allocator,
    app: *App,
    io: termio.Termio,

    // Methods take self explicitly
    pub fn close(self: *Surface) void {
        self.io.deinit();
        self.alloc.destroy(self);
    }

    // Can have const self for read-only methods
    pub fn hasFocus(self: *const Surface) bool {
        return self.focused;
    }
};

Tagged Unions

Powerful pattern matching with tagged unions:

pub const Action = union(enum) {
    print: u21,           // Associated data
    execute: u8,
    csi_dispatch: CSI,
    esc_dispatch: ESC,
};

// Switch must be exhaustive
switch (action) {
    .print => |codepoint| drawChar(codepoint),
    .execute => |byte| executeControl(byte),
    .csi_dispatch => |csi| handleCSI(csi),
    .esc_dispatch => |esc| handleEscape(esc),
}

Defer and Errdefer

RAII-like cleanup without destructors:

pub fn doSomething() !void {
    const resource = try allocate();
    defer resource.free();  // Always runs when scope exits

    const another = try allocateMore();
    errdefer another.free();  // Only runs if error is returned

    try riskyOperation();  // If this fails, errdefer runs
    // If we get here, defer runs when function returns
}

Common Patterns in Ghostty

The @This() Pattern

Files that define a single struct often start with:

const Surface = @This();
// Now 'Surface' refers to this struct throughout the file

Compile-Time Interface Selection

Ghostty uses comptime switches to select implementations:

pub const runtime = switch (build_config.artifact) {
    .exe => switch (build_config.app_runtime) {
        .none => none,
        .gtk => gtk,
    },
    .lib => embedded,
    .wasm_module => browser,
};

Scoped Logging

Each module has its own scoped logger:

const log = std.log.scoped(.surface);

// Usage:
log.debug("processing input", .{});
log.err("failed to render: {}", .{err});

Getting Started as a Contributor

Ready to contribute? Here's how to get started.

Development Setup

1

Install Zig 0.15.2+

Download from ziglang.org or use your package manager.

# macOS
brew install zig

# Check version
zig version  # Should be 0.15.2 or higher
2

Clone and Build

git clone https://github.com/ghostty-org/ghostty
cd ghostty

# Debug build (slow but has safety checks)
zig build

# Run directly
zig build run

# Run tests
zig build test
3

Platform-Specific Notes

macOS: Requires Xcode 26 and macOS 26 SDK (can build on macOS 15).

Linux: Install blueprint-compiler 0.16.0+ for GTK development.

Finding Issues to Work On

All issues in Ghostty are actionable. If you see an issue, it's ready to work on.

  • Contributor Friendly Issues - Great starting points
  • xterm Conformance - Terminal behavior fixes
  • Discussions - Feature discussions (issues come from approved discussions)

Useful Commands

# Build and run
zig build run

# Run with specific config
zig build run -- --font-size=16

# Run tests
zig build test

# Run specific test
zig build test -Dtest-filter="Parser"

# Check for memory leaks (Linux)
zig build run-valgrind

# Format code
zig fmt .

# Build libghostty-vt only
zig build lib-vt
